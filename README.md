# Morena Dlamini

I write software where a defect has physical consequences. Today that means
proximity-detection systems for underground mining — safety-critical code, in production,
audited. What I build outside that is the other half of the same problem: **ingest, APIs,
data models, and the asynchronous behaviour between them.**

**[worked-examples](https://github.com/MorenaDlamini/worked-examples)** — one repository,
readable in ten minutes. Each topic I study becomes a module: a written lesson, a set of
failing tests, my solutions, and a spoken answer. CI runs every module on every push; a
module is not finished because I say so. Start with
[`CONTRIBUTING.md`](https://github.com/MorenaDlamini/worked-examples/blob/master/CONTRIBUTING.md)
for the bar a module clears before it counts, and
[`NON-CLAIMS.md`](https://github.com/MorenaDlamini/worked-examples/blob/master/NON-CLAIMS.md)
for what the repository refuses to claim.

**Scope of the claim.** What my job evidences is production ownership under a constraint
where a defect hurts someone: determinism, defensive design, audit trails, review before
anything goes near a person. What the repository evidences is narrower — system design,
API design, data modelling, and the reasoning about asynchronous behaviour that goes with
them, against data I generate. Neither stands in for the other. Ask me where the boundary
is and I'll tell you precisely.

**Direction.** Data infrastructure, API design, and the security around both — the overlap
rather than either field alone.
[`CURRICULUM.md`](https://github.com/MorenaDlamini/worked-examples/blob/master/CURRICULUM.md)
names the specific roles it is aimed at and the exit test for every phase. It carries no
dates: a phase is over when its exit test passes, and how long that takes is an output of
the work, not an input to it.
